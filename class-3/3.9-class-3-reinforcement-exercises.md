# 3.9 Class 3 reinforcement exercises

Complete these five exercises in order. You will build a small catalog of games using last week's exercises as a starting point, then model its scores. Use PHP 8.4, strict types, typed members, and four-space indentation.

Copy your files from `src/Exercises/Class2` to `src/Exercises/Class3`. Add new files in the same folder.

Put `<?php` and `declare(strict_types=1);` at the top of every PHP file. Do not add closing PHP tags. Each class belongs in its matching file.

        // TODO: return the ID.
    }

1. Finish the methods. No method is abstract; the class itself is abstract because this catalog requires a specific kind of game.
2. Add empty `ArcadeGame extends Game` and `PuzzleGame extends Game` declarations in their matching files.

## Exercise 3-5: Model scores with an ERD

Create your diagram and rationale in `scores-erd.md`. A drawing exported from a diagram editor is also acceptable if you link it from this file.

Use these requirements:

* A Player has an ID and gamer tag; a Game has an ID and title.
* A Score has an ID, points, achievement time, one Player, and one Game.
* Players and games can exist before they have scores.
* A player may submit multiple scores for the same game.

Include all three entities, PK/FK labels, and the minimum/maximum participation at both ends of each relationship. Include two valid Score rows for the same player and game. Write both relationship directions in sentences.

Answer: Why would a unique constraint on `(player_id, game_id)` be wrong here? Why does a Score referring to a Game not imply `Score extends Game`? Do not create SQL or a database. Keep Game as one ERD entity; mapping the PHP subclass hierarchy to tables is beyond this exercise.

## Instructor answer guide

Exercise 3-1: the constructor calls `$this->setId($id)`; the setter throws for `$id <= 0`, then assigns `$this->id = $id`; the getter returns `$this->id`; description returns `'Game: ' . $this->title`. An abstract class need not contain abstract methods.

Exercise 3-2: both children are Games, but dynamic dispatch selects each object's override. Protected allows child access, not external access. The attribute catches the typo before the intended method can silently remain inherited.

Exercise 3-3: a complete final ArcadeGame body is:

```php
class ArcadeGame extends Game
{
    private int $maxPlayers;

    public function __construct(int $id, string $title, int $maxPlayers)
    {
        if ($maxPlayers < 1) {
            throw new InvalidArgumentException('Player count must be positive.');
        }

        parent::__construct($id, $title);
        $this->maxPlayers = $maxPlayers;
    }

    #[Override]
    public function describe(): string
    {
        return parent::describe() . ' / up to ' . $this->maxPlayers . ' players';
    }
}
```

Exercise 3-4: the final setter cannot be overridden; the final class cannot be extended. Private storage prevents direct child access to the parent's ID, while construction through the setter applies the same validation at creation. Final is not a complete guarantee that every possible subclass initializes itself correctly.

Exercise 3-5: Score contains `player_id` and `game_id` foreign keys. Each parent has `0..*` scores; each score has `1..1` of each parent. A separate score ID permits repeated player/game pairs. This is an association between stored records, not an is-a relationship. Accept alternative field names and drawing tools when the meaning is equivalent.
