# 7.0 Class 7 overview and tutorial roadmap

Class 7 covers Chapter 23, **Error Handling with Exceptions**, in *PHP Crash Course*. We will build a fresh, cumulative **Campus Dessert Planner** application using the existing student repository. The central question is: **If this operation fails, which part of the application can make a useful decision?**

The eight scripts below form a cumulative sequence. Complete the [five reinforcement exercises](7.9-class-7-reinforcement-exercises.md) and [ten-question comprehension check](7.10-class-7-comprehension-check.md) afterward.

By the end of class, students should be able to throw and catch exceptions, choose meaningful exception types, trace propagation, preserve valid object state, and decide whether to recover, provide a fallback, let a failure propagate, or end a request safely. Catching an exception does not itself repair the failed operation.

## Tutorial sequence

| Video | Script | Coverage and demonstration | Suggested length |
|---|---|---|---|
| 7.1 | [A fresh baseline and a failed promise](7.1-baseline-and-throw.md) | Create Food and Dessert classes, a setter called by the constructor, and the nested entry point. Throw Exception for negative calories before assigning the property. Compare valid construction, failed construction, and a failed update to an existing object. Read an uncaught stack trace in a controlled local demonstration. | 10–12 min |
| 7.2 | [Catching changes the path through the program](7.2-catching-and-control-flow.md) | Add a narrow try/catch; inspect getMessage in a local diagnostic example. Mark the statements that run, those skipped after throw, and where execution continues. Explain why code must not use a result whose construction failed or show a success message after failure. Distinguish controlled failure from successful recovery. | 10–12 min |
| 7.3 | [Different exception types, different responses](7.3-exception-types.md) | Introduce InvalidArgumentException for a negative value and a second exception for a value above the permitted maximum. Use multiple catches, specific before general, and test boundary values. Explain Exception, Error, and their shared Throwable interface; a TypeError signals a programming mistake to fix. | 10–12 min |
| 7.4 | [Custom exceptions describe the problem](7.4-custom-exceptions.md) | Create NegativeCaloriesException and ExcessiveCaloriesException with inherited constructors. Select responses by exception type rather than matching message text. Demonstrate why the model throws and leaves user-facing decisions to the caller. | 10–12 min |
| 7.5 | [Let the failure reach someone who can handle it](7.5-bubbling-and-boundary.md) | Move orchestration into Application and a page controller. Trace index → Application → controller → Dessert → setter. Catch a known input problem where a useful correction response can be prepared; leave other failures to propagate. Add a last-resort Throwable boundary around application construction and execution. Render a complete response before sending it; use a minimal independent error response if rendering itself fails. | 12–15 min |
| 7.6 | [What to do after catching an exception](7.6-responding-to-failure.md) | Build a Twig form with validated, normalized request input. On known domain failure, retain submitted values, explain the correction, and return 422 without claiming success. For an optional announcement decoded with JSON_THROW_ON_ERROR, catch JsonException and use a clearly identified default announcement. For an unexpected failure, return a generic 500 response and end the request. Compare these with rethrowing and with choosing not to catch. Discuss bounded retry only when a failure is temporary and repeating the operation is safe. | 15–18 min |
| 7.7 | [Finally is for cleanup](7.7-finally-and-cleanup.md) | Start with a trace marker to show finally on success and failure, then close an opened temporary stream in a try/finally example. Show cleanup while an exception propagates and before a pending return. Explain that cleanup does not undo completed work; avoid returning or throwing from finally because it can replace the original outcome. | 10–12 min |
| 7.8 | [Trace, choose, and verify](7.8-trace-and-verify.md) | Walk through the complete application's success, correctable input failure, optional-data fallback, and unexpected failure. Identify who throws, who catches, the response status, and whether the operation completed. Review empty catches, broad catches in every method, unconditional success messages, and endless retries. End with the bridge to next week's logging lesson. | 6–8 min |

The practical policy in 7.6 should be previewed throughout the earlier tutorials: every catch needs a reason and a specific response. The final tutorial consolidates the decision-making rather than introducing another application feature.

## The catch decision

| Situation | Useful action | What students must avoid |
|---|---|---|
| Expected bad input | Validate request shape first; catch a known domain exception, keep entered values, and explain how to correct them. | Treating every invalid form field as an exceptional event, or passing unvalidated strings to typed methods. |
| Optional feature fails | Catch its specific failure and provide an honest, safe fallback while preserving the main feature. | Inventing essential data or claiming the failed operation succeeded. |
| Current layer cannot help | Let the exception propagate; rethrow only when a catch has actually done useful work. | Catching merely because a method might throw, or catching and discarding the exception. |
| Unexpected application failure | At the request boundary, send a generic 500 response and stop that request's work. Fix the underlying defect during development. | Exposing raw messages or stack traces to visitors, or continuing with invalid state. |
| Temporary failure | Consider a limited retry only if repeating the operation is safe and likely to help. | Retrying invalid input, programming bugs, or operations with uncertain side effects. |
| Acquired resource | Release it in finally regardless of the operation's outcome. | Assuming catching or cleanup reverses earlier changes. |

The tutorials acknowledge that a generic response alone leaves no private diagnostic record. Next week adds logging at the marked boundary integration point. Logger setup, log levels, destinations, and detailed logging practices belong to that lesson.

## Five reinforcement exercises

The [exercise handout](7.9-class-7-reinforcement-exercises.md) contains five tasks. These five exercises build a separate cumulative **Campus Supply Quote** application under the exercise paths above, with original student names and presentation. They adapt the book's Product exercises without creating a new Composer project.

1. **Build the web form and Twig views.** Assemble a browser-only baseline and independent request boundary, preserve submitted scalar input, and escape it in Twig. Copy-and-adapt scaffolding is supplied.
2. **Validate and handle custom exceptions in the browser.** Implement Product and custom validation types, use specific-before-parent catches, and show an honest attempt marker in finally. Demonstrate preserved model state through a web view.
3. **Persist accepted quotes as JSON.** Save one server-named JSON record per quote outside public/, checking write results and cleaning up temporary files in finally. Show success only after persistence completes; distinguish 422 input corrections from 500 storage failures.
4. **Load saved quotes and handle built-in JSON failures.** Display persisted records in Twig and distinguish JsonException, UnexpectedValueException, and RuntimeException. Preserve corrupt files rather than silently resetting essential data.
5. **Handle an Error object and verify the complete policy.** Use a labeled web TypeError demonstration, verify the last-resort Throwable boundary and real temporary-file cleanup, and explain handling decisions and uncertain side effects.

Each exercise includes browser/editor acceptance checks. The exercises require no CLI work or StreamDemo adaptation. No database, external service, session, or logging package is required. JSON persistence is an exercise extension; the tutorial application remains unchanged.

## Ten-question comprehension check

The [comprehension check](7.10-class-7-comprehension-check.md) is supplied with ten questions, four choices each, exactly one correct answer, and an instructor key with brief explanations. Its coverage is:

1. Execution order after a throw.
2. The result of failed construction versus a rejected setter update.
3. Specific-before-general catch ordering.
4. Why a custom exception type is useful.
5. Call-stack propagation and the best layer to catch.
6. A meaningful response to correctable input.
7. When an optional fallback is appropriate.
8. When to leave a failure uncaught locally and when retry is inappropriate.
9. Finally as cleanup rather than rollback or recovery.
10. Exception versus Throwable and safe request-boundary behavior.

## Chapter alignment and instructor preparation

Tutorials 7.1–7.2 cover the chapter's basic throws and catches (listings 23-1–23-5). Tutorial 7.3 covers multiple built-in exception classes (23-8–23-9). Tutorial 7.4 covers custom exception classes (23-10–23-12). Tutorial 7.5 covers call-stack bubbling and the application boundary (23-13–23-14). Tutorial 7.7 covers finally (23-6–23-7), moved later so cleanup has a concrete purpose. Tutorials 7.6 and 7.8 supply the additional response-policy teaching requested for this class.

The book's dessert example is the starting model; the form, optional JSON notice, HTTP responses, and cleanup demonstration are course extensions. Keep the class 6 distinction between routing, page preparation, and Twig display, but introduce those pieces only after students can trace a basic throw/catch example.

Selected ideas from class 14 can support the discussion: error versus exception distinctions from 14.1, try/catch and Throwable from 14.3, request-shape checks from 14.6, and early validation and narrow responsibilities from 14.9. Rewrite these ideas for this week's paths and application. Do not reuse the database lessons or the broad catch/log/continue template as the default handling policy.
