# 7.8 Trace, choose, and verify the application

Keep the final 7.6 application and the restored 7.5 entry boundary. This lesson adds no application code. We will verify both execution and the reasons for our handling decisions.

## Trace a successful request

1. Browser posts scalar strings to `public/tutorials/class7/index.php`.
2. The entry loads the existing autoloader, creates Application, and calls run inside try.
3. Application selects the planner and passes POST input to DessertController::form.
4. The controller validates request shape and syntax, then constructs Dessert using a trimmed name and an integer.
5. The constructor calls the setter. The setter validates before assigning. No exception is thrown.
6. NoticeProvider supplies optional content. Twig renders the complete form and preview into a string.
7. The controller returns Response; Application returns it to index. Only then does index send the 200 status, content type, and body.

Ask students to identify the entry script, routing class, page preparation class, model, and display template. These roles continue class 6's separation.

## Trace three failure paths

| Failure | Throw or conditional? | Who handles it? | What happens next? |
|---|---|---|---|
| Missing or array-shaped calories | Request-validation conditional | DessertController | 422 form; no typed model call |
| Integer -1 or 5001 | Model throws a custom exception | DessertController | 422 form; values preserved; no preview |
| Malformed optional notice JSON | json_decode throws JsonException | NoticeProvider | Default notice; valid main preview still succeeds |
| Missing Twig template or an unexpected thrown programming failure | Thrown failure propagates | Entry Throwable boundary | One generic 500 page; request work ends |

The controller knows which field needs correction. The optional-content helper knows a valid default. Application cannot improve either outcome, so it does not catch. The entry boundary owns the final failure response, but it does not repair the defect. Logging that private diagnostic evidence is next week's addition.

## Verification checklist

Use the Network panel and inspect rendered content. Test query strings and POST values in a browser or constructed HTTP request; a plain CLI execution does not populate them.

| Test | Expected result |
|---|---|
| Fresh planner; unknown action; action[]=valid | 200 blank planner, no errors or result |
| Valid demo or valid POST | 200 preview, no correction list |
| Negative/excessive demo or POST | 422 correction; no Preview ready |
| 0 and 5000 | 200 preview |
| Missing fields, arrays, blank name, decimal text, leading-zero text, huge integer | 422; no raw warning or TypeError |
| Markup and quotes in the name | Escaped text in form and preview |
| Locally substituted malformed JSON or wrong JSON shape | Labeled default notice; valid preview remains 200 |
| Locally substituted missing template | One generic 500 document; no details or success body |
| StreamDemo CLI with valid and invalid calories | Resource closed before result delivery or caller catch |

Restore the correct JSON and template after fault demonstrations. The final excessive case should be 422, not the deliberately incomplete 500 policy from 7.5.

## Review tempting mistakes

- An empty catch discards the failure while offering no valid alternative.
- Catching Throwable in every method hides the intended handling layer and often mislabels defects as ordinary input problems.
- Echoing success after catch may claim an operation completed when it did not.
- Catching a model error and substituting an essential value such as zero produces misleading data.
- Retrying forever cannot fix an unchanged invalid argument and can repeat side effects.
- Returning from finally can replace the outcome; cleanup belongs there, response policy belongs elsewhere.
