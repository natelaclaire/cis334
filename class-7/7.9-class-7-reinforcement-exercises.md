# 7.9 Class 7 reinforcement exercises

Build a **Campus Supply Quote** application. Choose your own supply names and presentation. These five exercises build one cumulative application in a different context from the tutorials. A quote is only a preview: nothing is purchased, saved, or sent.

Keep the existing student repository, composer.json, composer.lock, App PSR-4 mapping, and pre-installed Twig. Do not create another Composer project or install packages. All paths below are relative to the student repository root:

```text
public/exercises/class7/index.php
src/Exercises/Class7/                      namespace App\Exercises\Class7
templates/exercises/class7/                outside public/
```

The entry loads `__DIR__ . '/../../../vendor/autoload.php'`. A controller directly in src/Exercises/Class7/ loads templates from `__DIR__ . '/../../../templates/exercises/class7'`. Use strict types, typed members and returns, four-space indentation, matching filenames, and no closing PHP tag. Twig must enable HTML autoescaping and strict variables. Keep form actions and links relative to the current index.php.

Start the server from the student repository root and open `/exercises/class7/index.php`:

```bash
php -S localhost:8000 -t public
```

Exercises 7-1 and 7-2 use the entry for CLI traces. Exercise 7-3 replaces it with the final web boundary. Keep any later CLI demonstration temporary and restore the web entry before submitting. No databases, sessions, external services, or logging package are needed.

## Exercise 7-1: Protect a Product's state

Create Product.php with private string name and float price properties, public getters/setters, and a constructor that uses the setters. The model holds a supplied unit price; no money calculations are required.

1. Trim names before storing them. Reject blank or whitespace-only names with InvalidArgumentException.
2. Reject a non-finite or negative price with InvalidArgumentException. Use is_finite to reject NAN and INF in direct PHP calls. Zero is allowed.
3. Reject a price greater than 1,000,000 with a general Exception for now. Exactly 1,000,000 is allowed.
4. Validate before assigning each property.
5. In the CLI entry, try valid and invalid construction in separate labeled attempts. Catch failures without using an object whose construction failed. Keep the success message on the successful path.
6. Create a valid Product, attempt a rejected name update and then a rejected price update. Print getters afterward to show that the previous valid values remain.

Import built-in exception classes in namespaced files. Do not compare diagnostic message strings to select responses.

| Test | Expected result |
|---|---|
| Study notebook, 4.50 | Object created; getters return accepted values |
| Name with surrounding spaces | Trimmed name stored |
| Blank or whitespace-only name | Rejected construction |
| -0.01 | Rejected price |
| 0 and 1,000,000 | Accepted prices |
| 1,000,000.01 | General exception |
| Direct PHP calls with NAN or INF | InvalidArgumentException |
| Rejected setter on a valid object | Previously stored value unchanged |

Explain why catching did not repair the bad value and why the setter's statement order preserves its old value. Do not claim an exception rolls back all earlier successful setters.

## Exercise 7-2: Handle specific failure types

Create EmptyNameException and ExcessivePriceException, both extending InvalidArgumentException. Empty class bodies with inherited constructors are sufficient.

1. Update Product to throw EmptyNameException for a blank name and ExcessivePriceException for a price above the maximum. Keep InvalidArgumentException for negative and non-finite prices.
2. Use specific catches for both custom types followed by InvalidArgumentException for the remaining known price problems. Supply a distinct actionable correction for each.
3. Temporarily put InvalidArgumentException first and verify that it intercepts its subclasses. Restore specific-first order.
4. Put an “operation completed” marker after construction inside try and an “attempt finished” marker after the catches. Predict and verify which appears on failure.
5. Temporarily change diagnostic message wording. Confirm type-based response selection is unchanged, then restore the wording.

Check: blank names, excessive prices, and negative prices reach the intended handlers. Valid products reach no handler. Completion appears only on success; the attempt marker appears after handled failures too. Classes autoload through the existing mapping.

Explain why types are more dependable than getMessage text for response selection. Explain why a wrong PHP argument type needs fixing rather than hiding behind a default Product.

## Exercise 7-3: Handle failure at the right layer

Create Application, an abstract Controller for Twig setup, ProductController, and Response (body string and status int), following 7.5–7.6. Adapt paths and namespaces to Exercises/Class7. Replace the entry with an exercise Application boundary: prepare the complete response inside try, catch unexpected Throwable objects, send a fixed generic 500 page, and return without success output.

1. Create base and quote templates with a name/price form posting to relative index.php. A fresh GET displays a blank form and no result.
2. Check fields are strings before trimming or conversion. Require a nonblank name of at most 80 bytes; document that this is a byte limit. Preserve scalar input for redisplay. Array-shaped input becomes blank text with correction errors.
3. Accept price text with an optional leading minus, a plain integer part without leading zeros except zero, and an optional decimal part of one or two digits. For example, 0, 4.5, 4.50, and -0.01 have valid syntax; 01, 4.567, 1e3, and +4 do not. Use `/^-?(?:0|[1-9][0-9]*)(?:\.[0-9]{1,2})?$/D` on trimmed text.
4. After the format check, convert to float and pass it to Product. Keep the model's finite/range checks: a huge string may convert to a non-finite float. Do not treat zero as failed conversion.
5. Catch the known model failures in ProductController, with specific types before their parent. Preserve submitted input, show approved correction text, and return 422 with no quote result. Ordinary shape/format errors also produce this correction through conditionals.
6. On success, display the accepted model name and formatted price with 200. Make clear it is a preview, not a saved purchase.
7. Let unexpected failures propagate through Application. Keep rendering outside the narrow model catch. The entry fallback must not reuse a failing Twig operation.
8. Prepare all HTML before sending headers or output. Mark the future logging integration point at the boundary in a comment; do not implement logging this week.

Check: fresh GET and valid POST return 200. Blank, malformed, negative, excessive, and array-shaped input return 422 without success output. Zero and the maximum succeed. Markup and quotes are escaped in form and result. Temporarily substituting a missing template locally produces one generic 500 document without a trace, path, or success result; restore the correct template.

Explain why the controller handles domain failures while Application does not catch them again. Explain why the entry's controlled 500 does not fix the underlying programming defect.

## Exercise 7-4: Recover an optional feature honestly

Adapt NoticeProvider from 7.6 to your exercise namespace and quote page.

1. Use `{"message":"Quotes are previews only; contact the campus shop to purchase."}` as normal input. Do not call an external service.
2. Decode with JSON_THROW_ON_ERROR. Catch JsonException in the helper and return a safe default plus a fallback flag.
3. Check successfully decoded content has a nonblank string message. Choose the default through an ordinary conditional for wrong shape or missing content.
4. Display “Default notice” when using the fallback. Escape all notice text with Twig.
5. Keep a valid quote usable despite an optional notice failure. Do not replace an essential failed price operation with zero.

Check normal JSON, malformed `{broken`, empty object `{}`, and `{"message":[]}`. A valid quote stays 200 in all four cases; the last three show the default label. A bad Product still gets 422 with either kind of notice. Restore normal JSON before submitting.

Explain why a default notice is safe while an invented price is not. Explain why retrying the same malformed JSON unchanged will not help.

## Exercise 7-5: Clean up and defend the policy

Adapt StreamDemo from 7.7 into QuoteStreamDemo using Product. Open php://memory, create and write a Product description, rewind/read it, return the description, and close the stream in finally. Use an events array to expose execution order, not a logger.

1. Check acquisition before entering the block that assumes the stream exists. Check writing, rewinding, and reading; throw RuntimeException for an unsuccessful operation.
2. Use try/finally without a local catch. Propagate domain failures to the demonstration caller.
3. Temporarily use the CLI entry to try valid and negative prices. Show closure before delivery of a successful return and before the caller catches the failure.
4. Do not return or deliberately throw from finally. Do not label cleanup as success or rollback.
5. Restore the web entry from Exercise 7-3 and recheck all quote and notice outcomes.

Check: both acquired streams close. The failed path has no returned description. The final web application still passes the 200/422 and optional-notice checks. Keep the helper in src/Exercises/Class7/; it needs no public route.

Explain what diagnostic capability is missing until next week's logging lesson. A generic 500 protects visitors from internal details but does not itself record evidence.
