# 6.9 Class 6 reinforcement exercises

Complete these five exercises in order after tutorials 6.1–6.7. Build a new cumulative **Campus Resource Center** site in the same student repository. Keep the existing Composer configuration and Twig installation. Create this week's exercise files from these requirements; do not move earlier lessons or import tutorial classes into the exercise application.

All exercises use `public/exercises/class6/index.php`, classes in `src/Exercises/Class6/` with namespace `App\Exercises\Class6`, and templates in `templates/exercises/class6/`. The entry script uses `__DIR__ . '/../../../vendor/autoload.php'`. The controller's template path is `__DIR__ . '/../../../templates/exercises/class6'`.

Use strict types, typed properties and return values, matching filenames, and four-space indentation. Run the existing server and open `/exercises/class6/index.php`. Use relative index.php links. No databases or sessions are needed.

## Exercise 6-1: Build a fresh two-page baseline

1. Create the entry script to load Composer, instantiate the exercise Application, and call run.
2. Create Application with Twig initialization, a run method that reads action, and private home and contact methods that render their respective views. Missing, unknown, and non-string actions must select Home.
3. Create base.html.twig with one HTML document, shared Home/Contact navigation, pageTitle and main blocks, and an h1 that repeats pageTitle using block(). Give each navigation link a block for its active class and include a small style rule that makes active links bold.
4. Create home.html.twig and contact.html.twig as children of base. Home introduces the resource center; Contact shows resources@example.com. Override the appropriate active-link block in each child.
5. Enable HTML autoescaping and strict variables when constructing Twig.

Check: Home and Contact have distinct titles and content; each has one active link. Unknown and array-shaped actions show Home. Identify where routing and rendering currently share one class.

## Exercise 6-2: Separate the front controller from display

1. Create DefaultController and put Twig initialization, home, and contact there.
2. Make its page methods public so Application can call them.
3. Replace Application's rendering logic with a run method that creates DefaultController and delegates through the action switch. Remove the former Twig setup and page methods from Application.
4. Keep the entry script and templates unchanged.
5. Write two sentences explaining the difference between selecting the action and generating its response.

Check: all requests from Exercise 6-1 produce the same visible results. Application contains no Twig rendering or HTML; DefaultController does not read the action parameter.

## Exercise 6-3: Add a privacy page

1. Create privacy.html.twig as a child of base. Use Privacy as its title and write two sentences of fictional practice content about the resource center's use of contact information.
2. Add a public privacyPolicy method to DefaultController to render that template.
3. Add an explicit privacy case to Application that calls the method.
4. Add a Privacy navigation link targeting `index.php?action=privacy` and a privacyLink block to base. Override that block with active in the new child.

Check: Privacy opens through navigation and a direct URL. The existing pages still work, all three pages show the new link, and only the current page's link is active. In your submission, name the four places you changed to connect the feature. This adapts the chapter's first exercise; the text is practice content, not a real policy.

## Exercise 6-4: Add a specialized staff controller

1. Create Staff with public typed string properties firstName, lastName, and email, initialized by its constructor.
2. Create StaffController with its own Twig setup for now. Give it a public staffList method that builds three Staff objects: Avery Chen / avery@example.com, Morgan Diaz / morgan@example.com, and Riley Patel / riley@example.com.
3. Pass those objects to staff.html.twig under the staff context key. Extend base and use a for loop to produce a table with First name, Last name, and Email headings. Include an else branch with an empty-state row spanning all three columns.
4. Create StaffController in Application::run and add a staff case that calls staffList.
5. Add `index.php?action=staff` to shared navigation with a staffLink block. Give the Staff child its title and active-link override.

Check: Staff displays all three rows and addresses. Temporarily pass an empty array and verify the empty-state row; then restore the objects. Application contains neither the staff data nor table markup. Notice the repeated initialization in your two page controllers before starting Exercise 6-5. This adapts the chapter's second exercise, with inheritance extracted next.

## Exercise 6-5: Extract and verify the shared superclass

1. Create an abstract Controller containing the template-path constant, protected Twig environment property, and public constructor that initializes Twig.
2. Make DefaultController and StaffController extend Controller. Remove their repeated setup, including their constructors. Keep all their page methods public.
3. Recheck Home, Contact, Privacy, Staff, missing action, unknown action, and an array-shaped action. Repeat the empty staff-list check and restore the data afterward.
4. Temporarily change one staff first name to `<em>Avery</em>`. The browser should display literal angle-bracket text, not italic markup. Restore Avery afterward.
5. Submit a short request trace for `?action=staff`, plus an explanation of why Controller is abstract, twig is protected, and staffList is public. Explain why inherited PHP setup and inherited Twig layout are separate mechanisms.

Check: the refactoring preserves the site's output; Twig setup exists only in Controller. Both concrete controllers use its inherited constructor, and no code tries to instantiate Controller itself. Include your route-check results and explanations with the exercise files.
